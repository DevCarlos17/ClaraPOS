# Exploration: CxC Sync Snapshot Redesign

> Change: `cxc-sync-snapshot-redesign` | Phase: explore | Project: clarapos

## 1. Problem & Context

ClaraPOS is an offline-first PWA (React 19 + PowerSync/SQLite + Kysely + Supabase/Postgres), multi-tenant, bimonetario. On a **new device**, cold-start sync currently takes **1-3 minutes** because the single PowerSync bucket (`by_empresa`, legacy `bucket_definitions`) ships **unbounded history** for ~50 tables with plain `SELECT * ... WHERE empresa_id = bucket.empresa_id` (no date window, no role filter) before the app can render anything useful — including a customer's outstanding balance.

Two constraints frame every option considered below:

1. **UI contract is frozen.** The CxC screens must keep showing "balance + pending invoices" exactly as today. Only the *data source* backing that read may change (local full-history scan → local snapshot read / partial sync).
2. **Alpha-stage leverage.** The app has no significant production data volume yet. This is the cheapest moment to fix the sync foundation (schema, triggers, authorization) before data volume makes migrations expensive or risky.

The core technical problem is: **today the customer balance and the "which invoices are pending" list are both re-derived by scanning full local history on every read** (SQLite aggregation over all-time rows), and PowerSync has no mechanism to let the sync layer ship only "the state that currently matters" versus "the history that explains how we got there." Fixing this needs two independent moves: (a) make the *read* O(1) via materialized/derived state columns, and (b) make the *sync* partial via time-windowed streams — without breaking (1).

## 2. Current State (verified against live code)

1. **Customer balance is already snapshot-based for the "deuda principal" ledger.** `movimientos_cuenta` carries a running balance per row (`saldo_anterior`, `saldo_nuevo` — `schema.ts:641-642`) and `clientes.saldo_actual` holds the last snapshot (`schema.ts:624`). An existing Postgres trigger, `actualizar_saldo_cliente()` (introduced in migration `0061`, sign-fixed in `migrations/0088_fix_saf_trigger_sign.sql`), fires on `movimientos_cuenta` INSERT and maintains `clientes.saldo_actual`. **This is the trigger this change's "one authority trigger" decision (D1/D2) will most likely extend, not replace from scratch.**

2. **Pending invoices are NOT state-flagged.** The pending-invoices list is computed as `WHERE CAST(saldo_pend_usd AS REAL) > 0.001` (`src/features/cxc/hooks/use-cxc.ts:145-160`, `:83-91`). `ventas` has `tipo` (`CONTADO`/`CREDITO`) and `status`, but `status` has a hard **2-value CHECK constraint**: `CHECK (status IN ('ACTIVA','ANULADA'))` (`migrations/0006_ventas.sql:179`). There is **no `estado` column** today.

3. **SAF (credit balance) is fully derived, not stored.** `SUM(SAFC) - SUM(SAF)` over **all-time** `movimientos_cuenta` rows for the client, no date filter (`use-cxc.ts:88-89`, confirmed duplicated client-side in `cxc-cliente-detalle.tsx:83`). Both `clientes` and `movimientos_cuenta` have `{ indexes: {} }` in `schema.ts` — **zero secondary indexes**, so this scan is a full unindexed table scan per read, per client.

4. **The UI already reads a split model, not the raw `saldo_actual` field.** `useDeudaFacturasClientes` + `useCreditoFavorClientes` are the real read paths; `clientes.saldo_actual` is kept write-side only, for ledger integrity — not read by the CxC screens directly. It currently has **17 write-sites** across `use-cxc.ts` (9), `use-ventas.ts` (3), `use-notas-credito.ts` (4), `use-importar-cxc.ts` (1) — all client-side `UPDATE clientes SET saldo_actual = ?` calls, independent of the one Postgres trigger in fact #1. This is live tech debt: the same value has two writers (client SQLite writeTransaction, and the server trigger on replication) that must agree.

5. **Reconciliation invariant (the correctness contract for this whole redesign):**
   `clientes.saldo_actual` (== last `movimientos_cuenta.saldo_nuevo`) **MUST equal** `SUM(ventas.saldo_pend_usd over pending invoices) − (SUM(SAFC) − SUM(SAF))`.
   Any new snapshot column (`estado`, `saf_disponible`) must preserve this identity or the UI's two independent reads (deuda list vs balance number) will silently diverge.

6. **Sync rules are legacy, single-bucket, no windowing, no role filtering** — verified directly against `backend/powersync-sync-rules.yaml` (repo copy, 160 lines): one `global` bucket (7 catalog tables) and one `by_empresa` bucket parameterized by `SELECT empresa_id FROM usuarios WHERE id = token_parameters.user_id` (line 62), covering ~58 tables with plain `SELECT * ... WHERE empresa_id = bucket.empresa_id`. **No `bucket_definitions` streams, no date window, no role/level parameter.** Important existing-convention detail for D3a: the `empresa_id` parameter is *already* resolved via a server-side SQL lookup keyed by the JWT's `token_parameters.user_id` — **not** a client-supplied parameter. Any role-based bucket (cajero/supervisor/propietario) should extend this same `parameters:` query pattern (e.g. `SELECT empresa_id, level FROM usuarios WHERE id = token_parameters.user_id`), which keeps role resolution server-trusted and consistent with current conventions (and with the Supabase security rule that authorization must never trust client-supplied or `user_metadata`-sourced values).

7. **`status='REVERSADA'` dead code.** `use-cxc.ts:151` excludes a `'REVERSADA'` status value from the pending-invoices query, but `ventas.status`'s CHECK constraint (fact #2) only allows `ACTIVA`/`ANULADA` — confirmed by grep across `migrations/0006_ventas.sql`. This is defensive code against a state that cannot exist in the current schema (dead, or a leftover from an earlier design that was never migrated).

8. **`vencimientos_cobrar` is unrelated to invoice CxC.** It tracks PRESTAMO installment aging, a separate sub-domain. The source of "pending invoices" is exclusively `ventas.saldo_pend_usd`.

9. **New finding — the `ventas` immutability trigger whitelists exactly which columns may change.** `prevent_venta_mutation()` (`migrations/0006_ventas.sql:195-230`, patched by `migrations/0097_permitir_reverso_saldo_venta.sql`) RAISEs an exception unless a `ventas` UPDATE touches *only* `saldo_pend_usd` (now bounded `≤ total_usd`, after the 0097 fix for payment-reversal reopening) and/or `status` (one-way `ACTIVA → ANULADA`). **Any new `estado` column on `ventas` will be rejected by this guard unless the guard function is updated in the same migration that introduces the column** — this is a concrete, already-proven failure mode in this codebase (0097 exists specifically because this guard silently discarded a legitimate reopening UPDATE via a FATAL Postgres error code the PowerSync connector swallows — `connector.ts:33`, `:665-678`).

10. **New finding — `movimientos_cuenta.tipo` CHECK constraint is closed-set and already covers reversal/credit semantics.** `migrations/0090_add_safc_tipo_movimientos_cuenta.sql:32`: `CHECK (tipo IN ('FAC','PAG','NCR','NDB','REV','SAL','SAF','SAFC'))`. This 8-value set is the exact input alphabet the new `estado`-deriving trigger must interpret per invoice to produce `pendiente / parcial / pago / reversado`.

11. **New finding — an in-flight sibling SDD change already attacked the sync-size problem with a *different* mechanism, and is only partially applied.** `openspec/changes/powersync-sync-scope-optimization/` has proposal+spec+design+tasks all written (not archived). Its approach: keep the **legacy `bucket_definitions`** format and add **concrete date-literal windows per table** inside `backend/powersync-sync-rules.yaml`, classifying tables as FULL / TRIMMED / OPEN-BALANCE-AWARE (`saldo_pend_usd > 0 OR fecha >= <window-literal>`) / NO-SYNC. It already:
    - Resolved the exact same "pending invoices must always sync" problem this change's Open Question (c) raises — via the OPEN-BALANCE-AWARE classification for `ventas`, `facturas_compra`, `gastos`, `vencimientos_cobrar`, `vencimientos_pagar`.
    - Resolved a role-based classification for `sesiones_caja` (cajero: own open session only; propietario: all active sessions) and a two-sided window for `citas` — directly relevant prior art for Open Question (d).
    - Required and got a **blocking prerequisite bugfix**, `bugfix-reversa-cxc` (migration `0097`, now live in `migrations/`), because of fact #9 above.
    - Ran one **live production spike**: Engram record `#4416` states a 4-day window literal was pasted into the **PowerSync Cloud Dashboard** for `movimientos_inventario` only. **However, the repo copy of `backend/powersync-sync-rules.yaml` does NOT contain that window** (verified: line 90 is still the unbounded `SELECT * FROM movimientos_inventario WHERE empresa_id = bucket.empresa_id`). Because this file is a "paste into the dashboard" artifact (not something PowerSync reads from the repo directly — see file header comment), **the actual deployed production sync rules may currently differ from this repo file**, and nobody can tell which is live by reading the repo alone.
    - None of the remaining slices (ventas OPEN-BALANCE-AWARE, role-gated `by_empresa_contable` bucket, `libro_contable` reclass) have been applied to the repo file yet.

    This is a **direct scope-overlap**, not a tangential one: D3b of this new change explicitly rejects "a dynamic date filter in sync rules" (the exact mechanism `powersync-sync-scope-optimization` is built around) in favor of Sync Streams with client-managed subscriptions. See §7 Scope Boundary for how this must be resolved before Proposal.

## 3. Closed Decisions (already made by the user — record, do not re-open)

| ID | Decision | Rationale |
|----|----------|-----------|
| **D1** | Invoice `estado` (`pendiente` / `parcial` / `pago` / `reversado`) is **derived by a PostgreSQL trigger**, never written by hand from the client. | A derived value must have exactly one source of truth. Today 17 client write-sites independently maintain `saldo_actual`-adjacent state — this pattern must not be repeated for `estado`. |
| **D2** | SAF availability gets a **dedicated materialized column** `saf_disponible` on `clientes`, maintained by the same trigger. ("Opción 1" — chosen over computing SAF on-demand from a trimmed sync window.) | O(1) read; no need to sync SAF movement history to compute it; keeps deuda and SAF explicit and independently inspectable, matching fact #5's reconciliation contract. |
| **D3a** | Sync **authorization** (role + empresa) goes through **JWT auth parameters** (server-side `parameters:` SQL resolved from `token_parameters`), **never** PowerSync client parameters. | PowerSync docs: client parameters are client-supplied and untrusted for access control. Matches the existing `empresa_id` resolution pattern already in `backend/powersync-sync-rules.yaml:62` (fact #6). |
| **D3b** | Time-windowing uses **Sync Streams with client-managed subscriptions** (accumulative window — device keeps what it already synced), **not** a dynamic date filter edited into legacy bucket queries (which slides and silently deletes now-out-of-window local rows on redeploy). | Avoids the data-loss-on-redeploy failure mode inherent to the legacy-bucket windowing mechanism (confirmed as the mechanism `powersync-sync-scope-optimization` is using — see fact #11). Accepted cost: client must persist which days/streams it has already subscribed to. |
| **Authority pattern** | **One** PostgreSQL trigger over `movimientos_cuenta` is authoritative for `saldo` + `estado` + `saf_disponible`. The 17 current write-sites are tech debt to consolidate into this trigger. **Hybrid model**: local SQLite writes an *optimistic* snapshot immediately (no triggers exist in SQLite/PowerSync's local DB), the server Postgres trigger is authoritative once the row replicates — "optimistic local write, authoritative server reconciliation." | Keeps the offline-first UX (instant local feedback) while giving the server a single, provable source of truth once online — matches how `actualizar_saldo_cliente()` already behaves for `saldo_actual` today (fact #1), just extended in scope. |

## 4. Open Questions for Proposal/Design

**(a) Exact trigger scope and offline-hybrid correctness.**
Given PowerSync's `writeTransaction()` model (local SQLite has no triggers — `CLAUDE.md` "Sincronización Offline" + confirmed no trigger definitions exist client-side), how is the **local optimistic value** of `estado`/`saf_disponible` computed and kept *locally consistent* before the server trigger's authoritative recomputation round-trips back down? Candidate approaches to compare in Design: (i) client computes the same derivation logic in TypeScript against local SQLite (duplicate logic, risk of drift — the same category of bug fact #9 describes between the trigger and the 17 write-sites); (ii) client writes raw movement rows only and shows "estado: syncing..." until the authoritative value replicates back (UX regression risk — contradicts "UI contract frozen"); (iii) some combination keyed off `saldo_pend_usd` (already client-optimistically maintained today) with estado as a pure, cheap client-side function of already-present fields, reconciled by replication. **Must be resolved before Design**, this is the single highest-risk open question.

**(b) Backfill/migration plan for existing rows.**
Populating `estado` and `saf_disponible` for every pre-existing `ventas`/`clientes` row cannot be a single blind `UPDATE` if it needs to derive `estado` from the full `movimientos_cuenta` history per invoice (fact #10's 8-value alphabet) — and it must **never** touch `movimientos_cuenta` itself (immutable ledger, enforced by `trg_kardex_no_update`-equivalent guards per CLAUDE.md rule #2). Needs: a read-only backfill query/function that computes `estado` from existing immutable history and a single `UPDATE ventas SET estado = ...` pass (one-time, not touching the ledger), run before the trigger goes live, with the trigger taking over going forward. Must be sequenced against `prevent_venta_mutation()` (fact #9) — the guard function must accept the new column in the *same* migration, or the backfill UPDATE will be rejected exactly like the pre-0097 reversal bug was.

**(c) Which tables are time-windowed vs always-synced.**
**CRITICAL, already has a proven-in-production precedent and failure mode to avoid**: `powersync-sync-scope-optimization`'s OPEN-BALANCE-AWARE classification (fact #11) already solved "pending invoices must always sync regardless of window" for the legacy-bucket mechanism. This change must re-derive the equivalent guarantee for Sync Streams: if `estado`/`saf_disponible` become the read path (O(1), no full-history scan needed), does that *remove* the need for "always sync open invoices," or does the UI still need the actual pending `ventas` rows (for the invoice list, not just the aggregate number) and therefore still need an open-balance-aware stream? Likely answer: yes, still needed — the balance number becomes O(1) via snapshot, but the **invoice list** itself is still individual rows that must be present locally. Must enumerate per-table in Design, not assume the snapshot alone solves windowing.

**(d) Role → table authorization matrix.**
Cajero vs Supervisor vs Propietario (levels 3/2/1). `powersync-sync-scope-optimization`'s owner-approved resolution for `sesiones_caja` (fact #11) is directly reusable prior art: cajero sees only their own open session, propietario sees all. Design must produce the equivalent matrix for whichever tables this change's scope actually touches (likely narrower than the sibling change — see §7).

**(e) PowerSync Sync Streams edition migration and coexistence with legacy buckets.**
Sync Streams is a newer PowerSync primitive (requires a specific sync rules "edition"). Unverified from this codebase (no Sync Streams usage exists yet anywhere in the repo): can an instance run `bucket_definitions` (legacy) and Sync Streams simultaneously during a transition, or is it an all-or-nothing edition switch? This gates whether the rollout can be incremental table-by-table or must cut over the whole `by_empresa` bucket at once. **Needs a PowerSync-docs spike in Design**, not an assumption — flagged exactly like the sibling change flagged its own windowing-mechanism uncertainty before resolving it via Context7-verified docs (per Engram `#4384`).

**(f) The `REVERSADA` ghost (fact #7).**
Either (i) implement it as a real `estado` value now that a trigger-derived state machine exists (natural fit — "reversado" is already one of D1's four named states), or (ii) delete the dead defensive code in `use-cxc.ts:151`. Given D1 explicitly names `reversado` as a state, (i) looks like the intended resolution — Design should confirm and remove the now-redundant client-side filter.

**(g) Module × movement × estado interaction matrix.**
Must map all 8 `movimientos_cuenta.tipo` values (fact #10) and all call sites that mutate `ventas.saldo_pend_usd` (CxC payments, `use-ventas.ts` contado/credito creation, `use-notas-credito.ts` NC application, reversal) against the 4 target `estado` values, explicitly covering: NC reduces *monto exigible* without counting as *abonado* (does a full-NC invoice become `pago` or a new state?); reverso re-opens (`pago`/`parcial` → `parcial`/`pendiente`, already unblocked by migration 0097); `CONTADO` + later NC must settle back to `pago`, not stay `parcial` forever. This matrix is Design-phase work, not Explore — flagged here so it isn't dropped.

## 5. Approaches Compared (sync-windowing rollout strategy)

| | **A. Big-bang cutover** | **B. Incremental coexistence (recommended)** |
|---|---|---|
| **Description** | Ship schema changes (estado, saf_disponible, trigger, backfill) + Sync Streams migration + full role/time-window authorization matrix in one coordinated release. | Sequence into independently-shippable slices: (1) schema + trigger + backfill (no sync-rule change — pure correctness/perf win on local reads, zero sync-size change yet); (2) Sync Streams spike/migration in isolation (verify edition coexistence, §4e); (3) per-table time-window + role rollout, one table/module at a time, reusing the `powersync-sync-scope-optimization` classification work already done. |
| **Pros** | Single reconciliation window; no intermediate "half-migrated" state to reason about. | Each slice is independently testable/revertible in production (no staging environment exists — confirmed by the sibling change's rollout notes); reuses already-resolved classification decisions (sesiones_caja, citas, ventas OPEN-BALANCE-AWARE) instead of re-deriving them; isolates the highest-risk unknown (§4a offline-hybrid trigger correctness) into its own slice before touching sync rules at all. |
| **Cons** | No staging PowerSync/Supabase environment exists (confirmed fact from sibling change's rollout notes) — a big-bang release is a single, large, hard-to-roll-back production change on financial data. | Longer calendar time to full benefit; requires explicit scope-boundary negotiation with the overlapping sibling change (§7) at every slice. |
| **Effort** | Medium (less coordination overhead) | Medium-High (more sequencing/PR discipline, offset by directly reusing prior-art decisions) |

**Recommendation: B.** The codebase has zero staging environment for PowerSync/Supabase (verified precedent: the sibling change ran its only validation as a live, reversible, single-table production spike — fact #11). Financial-data correctness changes (trigger authority over `saldo`/`estado`/`saf_disponible`) must not ship in the same atomic change as a new, unverified sync primitive (Sync Streams, §4e) on an alpha-but-live system. Slice 1 (schema + trigger + backfill) delivers real value — faster local reads, single source of truth — **before** any sync-rule risk is introduced, and de-risks §4a in isolation.

## 6. Risks to Production & UI

- **Balance-depends-on-local-pending-invoices risk.** Per §4c, even after `estado`/`saf_disponible` make the aggregate number O(1), the invoice *list* UI still needs actual `ventas` rows present locally. If a future time-window change ever evicts a pending invoice row from local storage (the exact mechanism fact #11 proved can happen with legacy-bucket literal windows on redeploy), the balance number and the invoice list can diverge even though both are "fast." This is a correctness risk independent of which sync mechanism (legacy bucket vs Sync Streams) is chosen — it must be an explicit invariant test in Design/Verify, not an assumption.
- **17-write-site blast radius.** Consolidating `saldo_actual` (and adding `estado`/`saf_disponible`) maintenance into one trigger means auditing and eventually retiring 17 existing client write-sites across 4 files. Each retirement is a behavior change on a financial write path; must be staged and tested individually, not as one sweeping refactor.
- **Trigger split-logic cost (offline-hybrid, §4a).** Whatever local-optimistic computation is chosen will inevitably diverge from the server trigger's authoritative computation under edge cases (concurrent devices, delayed sync, partial history locally present). This is the same bug *category* that produced the pre-0097 silent-discard bug (fact #9) — a guard or reconciliation UPDATE can be silently rejected by an immutability trigger if the new column isn't accounted for in the same migration.
- **Backfill vs ledger immutability.** The backfill (§4b) must derive `estado` from `movimientos_cuenta` history **read-only** — any accidental write path that touches `movimientos_cuenta` itself during backfill would violate the immutable-ledger rule (CLAUDE.md rule #2) and the enforcing DB triggers.
- **Scope collision with `powersync-sync-scope-optimization`.** Two SDD changes targeting the same file (`backend/powersync-sync-rules.yaml`) with two different, D3b-incompatible mechanisms (legacy date-literal windows vs Sync Streams) cannot both proceed to `apply` independently without one superseding or absorbing the other. See §7.
- **Repo/production drift on sync rules.** Fact #11's dashboard-vs-repo mismatch means the actual currently-live sync rules are not fully knowable from the repo alone. Any change to `backend/powersync-sync-rules.yaml` in this change must explicitly re-paste the *entire* file into the PowerSync Cloud Dashboard (not a partial diff) to guarantee repo == production, and should include a step to manually read back the dashboard's current live rules before editing, to avoid clobbering an undocumented live spike.
- **JWT role-claim source.** Per the Supabase security checklist (loaded this session): authorization data must come from `app_metadata`/a server-side table lookup, never `user_metadata`. The existing `empresa_id` parameterization already does this correctly (table lookup via `token_parameters.user_id`); D3a's role parameter must follow the exact same pattern, not a JWT custom claim sourced from user-editable metadata.

## 7. Scope Boundary

**IN scope for `cxc-sync-snapshot-redesign`:**
- New `estado` column (trigger-derived) on `ventas`; new `saf_disponible` column (trigger-derived) on `clientes`.
- Consolidation of the authority trigger over `movimientos_cuenta` → `saldo_actual` + `estado` + `saf_disponible`.
- Backfill migration for existing rows.
- The CxC/pending-invoices/SAF read path specifically (the "balance + pending invoices" UI contract named in the problem statement).
- Resolving how this change's Sync Streams + JWT-role-authorization approach (D3a/D3b) relates to, and must reconcile with, the already-partially-applied `powersync-sync-scope-optimization` change (this reconciliation itself is in scope for the Proposal phase — it cannot be deferred, since both touch the same production file).

**OUT of scope (explicitly named by the user as related-but-separate, or discovered during this exploration as pre-existing/separate work):**
- Contabilidad (`libro_contable`) sync removal/reclassification — already scoped inside `powersync-sync-scope-optimization`'s Slice 3; not duplicated here.
- Device-count limiting — mentioned by the user as related; no code evidence found of related work; treat as a fully separate future change.
- Sesiones de caja sync scoping by role/state — already resolved as decisions inside `powersync-sync-scope-optimization` (fact #11); this change should **consume** that resolution if the sibling change is superseded/absorbed, not re-decide it.
- Tesorería/Caja propagation of payment reversals (Engram `#4406`'s "feature #3") — explicitly already assessed as NOT required for CxC balance correctness and independent of this change.
- The "view older data from Supabase when online" on-demand fetch paths (agenda, contabilidad, closed sessions) — explicitly deferred as a separate follow-up by the owner during the sibling change's design session (fact from Engram `#4384`).

**Must be resolved in Proposal, flagged here so it is not silently dropped:** whether `cxc-sync-snapshot-redesign` **supersedes** `powersync-sync-scope-optimization` (abandoning its legacy-bucket-windowing design.md/tasks.md in favor of Sync Streams) or **sequences after it** (ship the sibling's already-designed, already-partially-applied legacy windowing first, then migrate the mechanism to Sync Streams in a later change). Given D3b's explicit rejection of the sibling's core mechanism, superseding looks more consistent — but that decision has production-rollback implications (fact #11's live dashboard spike) that only the Proposal phase, with the user, should formally close.
